# ADR-0033: Club identity is seeded from the world seed, never from the per-tier provisioning seed

- **Status:** Accepted
- **Date:** 2026-09-29
- **Stage:** 12
- **Related:** [ADR-0005](0005-dynamic-pyramid-and-backfill.md), [ADR-0030](0030-provisioning-execution-and-bootstrap-provenance.md), game rules `FIC-4`, `FIC-7`, `PYR-11`, `PYR-14`, master plan §3.2, §6.3, §16 Stage 12

## Context

`ClubIdentityGenerator` names the eighteen clubs of a tier by walking a country's shared name cycle. Each
club is placed at `(countryOrdinal + offset) % CombinationsPerCycle`, where `countryOrdinal` folds the tier
in (tier 1 takes ordinals 0–17, tier 2 takes 18–35, …) and `offset` is drawn from the **seed the caller
hands the generator**. The generator's own remarks, and the guard test
`Ordinals_do_not_restart_per_tier_so_generated_tiers_never_collide`, argue that folding the ordinal into the
cycle keeps a provisioned tier from colliding with the tier above it.

That argument holds only when every tier of a country draws the **same** offset, which means the **same**
seed. It did not. The world seeder passed the raw world seed (`SeedWorld` → `WorldGenerator.BuildTier`);
the provisioning worker passed `request.GenerationSeed`, which `CapacityEvaluator.GenerationSeedFor`
derives from the world identity, the country code, and — deliberately, for retry reproducibility — the
**target tier**. So tier 1 and tier 2 placed their eighteen-slot windows independently on a
220-slot cycle and overlapped roughly 35/220 ≈ 16% of the time, which the unique index
`ux_clubs_world_id_normalized_name` rejected with Npgsql 23505. In production that dead-letters a
provisioning job; in the test suite it was an intermittent ~40% failure.

The question this ADR settles is: which seed names the clubs of a provisioned tier?

## Decision

**1. Club identity is always seeded from the world's generation seed.** `WorldGenerator.BuildTier` takes the
club-identity seed from a new `TierGenerationRequest.WorldSeed`, not from `TierGenerationRequest.Seed`. The
seeder passes the world seed for both; the provisioning worker passes the world seed for identity and the
per-tier request seed for everything else.

**2. One seed, two roles.** `Seed` seeds the tier-scoped content — the division-season's schedule seed and
tie-draw seed (`DivisionProvisioningGenerator`), and the generated squads (`PlayerGenerator`). `WorldSeed`
seeds club identity only. Splitting them keeps both properties that matter: a retried provisioning request
reproduces the same tier (its request seed is stored and reused), and every tier of a country draws the same
name offset (its identity seed is the world seed, which never varies).

**3. The worker reads the world seed from the bootstrap run.** `IGenerationRunRepository.FindWorldSeedAsync`
returns the seed of the single `world_bootstrap` `GenerationRun`. The seed is already persisted there
(`SeedWorld` records it), so no schema change is needed. If it is ever absent at provisioning time the
worker fails permanently: a tier cannot be named without it.

**4. The provisioning generator is versioned forward.** `DivisionProvisioningGenerator.Version` becomes
`division-gen-v2`, because a provisioned tier's club names now differ under the same request seed, so a tier
generated by `division-gen-v1` is not reproducible by v2 and must be labelled as such. The world seed is
folded into `InputHashFor` so a rerun under a different world seed is explainable rather than looking like a
reproducibility bug. The bootstrap's own output is unchanged (tier 1 already used the world seed), so
`WorldBootstrapGenerator.Version` and `ClubIdentityGenerator.Version` stay put.

## Consequences

**Positive**

- A country's tiers are named from one offset and one ordinal walk, so their names are disjoint by
  construction from tier 1 upward, however the tier was created (`PYR-11`).
- The provisioning flake disappears, and the underlying production defect — a tier that dead-letters on a
  name collision — is fixed rather than retried around.
- The two seeds are now explicit in `TierGenerationRequest`, so a future caller cannot silently reintroduce
  the coupling.

**Negative**

- Tier 1's names are unchanged, but every tier provisioned under `division-gen-v1` has different names than
  the same tier would under v2. There are no production worlds yet, and the version label makes the change
  visible in `world.generation_runs`.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Derive identity from the world **id** and country code | Breaks "the same generation seed reproduces the same logical world" (Stage 3 exit, `WorldSeedingTests`): two worlds seeded from one seed string would be named differently. |
| Rederive the whole country seed per tier (drop `targetTier` from `GenerationSeedFor` and use it for identity too) | Tier 1 would still use the raw world seed while tier N used a derived one, so the offsets would still differ; the identity seed must literally be the world seed. |
| Retry generation on a name collision | Hides a determinism defect behind a retry loop, and would need a bounded retry and a new failure mode. The generator's whole design is that names are unique without a retry. |
| Store the world seed on `game_worlds` | A migration for a value already persisted in `world.generation_runs`; `FindWorldSeedAsync` reads it without a schema change. |
