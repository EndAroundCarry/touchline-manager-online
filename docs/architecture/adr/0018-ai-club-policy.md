# ADR-0018: A club nobody manages is set up by a pure, versioned policy run by the worker

- **Status:** Accepted (decision 2's neutral `balanced`/`normal` training is superseded by [ADR-0057](0057-training-programmes-age-curve-and-hidden-aptitude.md): an AI club trains each player's position-default programme at normal intensity, by the same rules as a manager)
- **Date:** 2026-09-27
- **Stage:** 8
- **Related:** [ADR-0003](0003-postgresql-durable-jobs.md), [ADR-0014](0014-matchday-lock-resolution-and-publication.md), master plan §7.2, §7.3, §16 (Stage 8), game rules `INS-9`, `INS-10`, `INS-11`, `INS-12`, `TRN-1`, `OCC-2`, `OCC-5`, `WORLD-7`, `WORLD-9`

## Context

Stage 6 made a fixture playable before anyone had opened the tactics screen: a club with no saved plan takes
the field in `MatchSnapshotBuilder`'s default formation with the neutral instruction set, and the builder
decides its eleven deterministically. That kept the world playable, but it is a repair path, not a manager.
Until this milestone every AI club in the world fielded the same neutral 4-4-2 and trained at the implicit
`balanced`/`normal` default, so `INS-12` — "humans and AI are validated by the identical validator; AI
receives no bypasses" — had only half its subject: an AI club had *a* legal side, not *its* side.

Four decisions in giving the AI real plans are expensive to change once a world is running.

**1. Where a club's decisions come from.** They could be generated and stored once when the world is seeded,
or decided on demand by a rule. A stored draw has to be generated by *something*, and that something is a
rule either way.

**2. Whether the AI's tactics vary.** A league of eighteen identical neutral sides is not a football league;
but a choice made permanent and invisible is a fairness problem.

**3. What the AI does to a plan that already exists.** A club may have a plan because a manager set it, or
because a previous evaluation did. A small change here silently destroys a manager's work or a club's
inherited state.

**4. Who runs the AI.** The matchday builder runs inside the lock workflow; training runs in a daily job.

## Decision

**1. The AI's decisions are a pure, versioned rule (`ai-policy-v1`), seeded from the club's identity.**

`AiClubPolicy.Decide(clubId, squad)` is a pure function in `Domain/Squad`: it reads no clock, database,
culture, or global random source, and every draw comes from a `Pcg32` stream seeded from the club identity
and the policy label. The same club always decides the same way, a different club draws differently, and
changing the draw order, the formation list, or the selection order is a named policy version rather than a
silent constant — exactly as `training-v1` and `match-load-v1` version themselves above. It returns the
formation, the eight instructions, the default eleven, and the training choice in one value.

**2. The AI varies its tactics and does not vary its training.**

The formation and the eight instructions are drawn per club, because variety is what makes a division a
division and every choice is one the engine already bounds (`INS-9`). The training choice is not drawn: a
training focus is a persistent development path rather than a match-to-match lever, so a club permanently
dealt a random focus would be a fairness problem dressed as variety. Every AI club trains at the neutral
`balanced`/`normal`, which is what the progression job already assumes for a club with no plan (`TRN-1`).

**3. The evaluation fills gaps and never overwrites.**

`EvaluateAiClubs` writes a default plan only when the club has none, and a training plan only when the club
has none. A plan a previous run wrote, or a manager wrote, is left exactly as it is. That is what makes the
job safe to run at least once — the second pass writes nothing — and what keeps `WORLD-9` and `OCC-5` true:
a takeover inherits a working side, and a resignation does not reset the club.

**4. The evaluation is a worker-only, daily materialised job.**

`world.evaluate-ai-clubs` is a durable row keyed on the UTC day, placed by `AiClubScheduler` exactly as the
matchday and progression schedulers place theirs (ADR-0003). It is registered only by `AddJobQueueWorker`, so
an API process can never write a squad plan, and a worker that was down when the day opened runs the
evaluation late rather than skipping it. Only clubs with **no open tenure** are considered — an inactive
tenure still occupies its club (`OCC-8`), and making safe decisions on a manager's behalf while they are away
is the inactivity ladder's work (`OCC-2`), which Stage 11 owns.

**5. Every AI plan is accepted by the human validator before it is written.**

The evaluator builds the policy's decision into `TacticalSlotDefinition`s and passes them through
`TacticalPlanValidator` — the same function a manager's save calls. A plan the validator refuses is not
written and is counted, so `INS-12` is enforced by the code path rather than by intention. This is how the
first version's defect was caught in development: the empty-lineup case was building `Guid.Empty` occupants,
which the validator rejected as `PLAYER_NOT_ELIGIBLE`.

## Consequences

**Positive**

- An AI club has a real, persisted side and training plan a manager inherits, rather than a formation the
  builder synthesises and discards on every lock.
- The AI's decisions are reproducible from the club identity and the policy label, so a world can be
  replayed and two runs cannot diverge.
- The AI is validated by the same rule as a human, so it cannot acquire a side the game would refuse a
  manager.
- The job is idempotent and gap-filling, so at-least-once delivery and a mid-run crash are both safe.

**Negative**

- The evaluator adds a write path to the squad module that no command reaches, which is a second author of
  `squad.tactical_plans` and `squad.training_plans` beside the save use cases. Both go through the domain
  factories and the same validator, so the rules stay in one place, but the authorship is split.
- A club's plan is fixed until a manager changes it: the AI does not re-pick its eleven as injuries and
  transfers move the squad. That is deliberate — the snapshot builder already repairs an unavailable or
  ineligible pick at the lock (`DIS-6`), and re-picking on every evaluation would rewrite a manager's plan
  the moment they resigned. A state-reactive AI lineup is a later feature if balance needs it.
- `AiClubRepository` reads across the world and squad schemas in one query set, because "who is
  AI-controlled" and "what may they pick" is one question. The project already accepts this shape of
  cross-module read in the matchday repository.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Generate and store each AI club's plan during world seeding | The bootstrap would own squad decisions that `SeedWorld`'s remit does not cover, and a club that *becomes* AI-controlled later (a resignation, or Stage 11's provisioned tier) would need the same generator anyway. A rule plus a job covers both. |
| Have the snapshot builder decide the AI's tactics too | The builder freezes *a* side; the plan is a durable artifact a takeover inherits and a manager can edit, which a per-lock synthesis is not. It would also put a game-balancing choice inside a workflow that must stay a reducer. |
| Pick the AI's training focus per club | A permanent development path chosen at random is a fairness problem, not variety. The neutral choice is identical for every AI club, so it cannot tilt competition, and the trade-off stays the manager's. |
| Re-evaluate on every lock and overwrite the AI's plan | Would rewrite a manager's inherited plan on a resignation and bump versions with nothing new to say. The builder's repair is the right place to absorb a changed squad. |
| Let the AI evaluation run from the API | The API must never advance a deadline or write a game decision (`MAT-2`'s principle); the scheduler is registered beside the queue poller so only the worker can. |
